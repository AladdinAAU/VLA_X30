1 UDP Command

The communication between the motion host and the perception host (or controller)
adopts UDP protocol, which stores the raw data in little endian.

1.1 Protocol Format

This section contains the introductions of the raw data format of UDP transmission. Based
on whether carrying the complex data, UDP commands can be divided into two categories:
Simple command and complex command.

1.1.1 Simple Command

The format of simple command is [xxxx yyyy zzzz], and one letter represents one byte.

Simple commands use the structure CommandHead to store the content of raw data.

1 struct CommandHead{

2     uint32_t code;

3     uint32_t paramters_size;

4     uint32_t type;

5 };

xxxx is the value of CommandHead.code , which represents the command code.
yyyy is the value of the CommandHead.paramters_size , representing the command
value of the command code. If the command code has no valid command value, yyyy = 0.

zzzz is the value of CommandHead.type , which is used to distinguish the command types.

The type value of simple command is 0, that is, zzzz = 0.

The use case is as follows:

1 //routine

2 struct CommandHead command_head = {0};

3 command_head.code = 1;        //Command code

                                          6/ 68
                                   DEEPRobotics

4 command_head.paramters_size = 0;// Command value

5 command_head.type = 0;           // Command type

6 sendto(sfd,&command_head,sizeof(command_head),Target address, address size )

1.1.2 Complex Command

Complex commands carry the specific data content in the format of [xxxx yyyy zzzz

bbbbbbbb......] , where one letter represents one byte.

Complex commands use the structure Command to store the content of raw data.

1 struct CommandHead{

2      uint32_t code;

3      uint32_t paramters_size;

4      uint32_t type;

5 };

6 const uint32_t kDataSize = 256;

7 struct Command{

8      CommandHead head;

9      uint32_t data[kDataSize];

10 };

xxxx is the value of Command.head.code , which represents the command code.
yyyy is the value of the Command.head.paramters_size , representing the length of the
data content bbbbbbbb.......

zzzz is the value of Command.head.type , which is used to distinguish the command
types. The type value of complex command is 1, that is, zzzz = 1.

bbbbbbbb...... is the value of Command.data , which represents the data content carried
by this command.

The use case is as follows:

1 //routine

2 int32_t to_be_send_data[64];

3 struct Command command = {0};

4 command.head.code = 52; // Command code

5 command.head.paramters_size = sizeof(to_be_send_data);// Data length

6 command.head.type = 1;          // Command type

                                           7/ 68
                                      DEEPRobotics

7 memcpy(&command.data,&to_be_send_data,sizeof(to_be_send_data));
8 sendto(sfd,&command,sizeof(command.head)+command.head.paramters_size,Target address, address

     size);

Taking joint velocity as an example:

1.2 Send Command to Motion Host

The controller and perception host directly issue commands to the motion host through
UDP communication, so as to control the robot to achieve corresponding functions.
The target IP and port for the perception host or controller to send messages to the
motion host are: 192.168.1.103:43893 .
However, please note that sending a message does not change the original control logic.
For example, when the robot is lying down, the command of start motion does not work,
and the control logic still follows the robot's own motion logic.

                                             8/ 68
                                DEEPRobotics

[Notes] All command codes in hexadecimal format introduced in this section use the first two
digits to distinguish the sender source:
When sending command codes from a remote control terminal (e.g., a controller), the first
two digits should be 0x21 (e.g., 0x21040001).
When command codes are issued by autonomous movement algorithm modules (e.g., a
navigation module), the first two digits should be 0x31 (e.g., 0x31040001).
In subsequent descriptions, command codes will be presented with 0x21 as the default
starting prefix unless otherwise specified.

1.2.1 Heartbeat

The heartbeat is used to confirm whether the connection is normal. Please follow the

steps below to send heartbeat.

1. To maintain the connection, continuously send the following heartbeat command

code at a frequency of no less than 2 Hz. If a transmission timeout occurs, the motion

program will assume the connection is disconnected:

Command code                    Command value        Command type

0x21040001                      -                    0

      [Notes] The minus sign "-" in the command value indicates that this value does not work,
      that is, the command value will not have any effect on the command.
2. After initiating continuous transmission of the heartbeat command code 0x21040001,

you must send the following instruction once to confirm the connection:

Command code                    Command value        Command type

0x21020001                      -                    0

Axis command is the command output from x-axis and y-axis of the two joysticks of the
controller, with a value range of: [-32767,32767]. The issue frequency of axis command
should be 50Hz. If the motion host has not received any axis command for more than one
second, the command will be considered as invalid by the system.

1.2.4 Control Mode Command

The control mode determines the source of the velocity command that the robot

responds to. In the non-manual mode, the robot responds to velocity commands from the

perception host; and in the manual mode, the robot responds to velocity commands from

the controller.

1.2.7 Save Data Command

last 5 minutes and automatically exit the motion program.

If the jy_exe program is version v2.2.45 or higher:

Command code               Command value                   Command type

0x010C01                   -                               0

If the jy_exe program is below version v2.2.45:

Command code               Command value                   Command type

1.4 Command Set of Autonomous Charging

Autonomous Charging mainly includes the following states:
1. Idle State: The robot is waiting for the Start Charging Command, and is not executing

    a charging task.
2. Startup State: The robot enters the charging dock, adjusts its posture, and lies down

    on the charging dock after it receives the Start Charging Command.
3. Charging State: The robot is actively charging using the charging dock.
4. Exit State: The robot stands up and leaves the charging dock after it receives the

    Stop Charging Command.
5. Power Failure: If the robot fails to detect the charging current during charging, it will

    enter this state until the charging current is detected again.
6. Error State: The state in which the robot encounters anomalies during startup.

1.5 Command Set of Elevation Map Module

Elevation map module has the following two functions:
1. Footstep planning: While climbing stairs, the Elevation map module delivers 3D

     information about the surrounding obstacles to the motion program in order to plan
     the exact contact location and make stair climbing more stable.
2. Collision detection: In non-manual mode, the elevation map module detects the risk
     of collision in real time, and updates the input speed (axis commands from joystick or
     velocity commands issued by the navigation module) so that the robot slows down
     and stops or goes around the obstacles, thus avoiding collision.

1.5.1 Velocity Input Source

Developers can choose the velocity command input source of the elevation map: axis
command of joystick or velocity command from navigation.

               29/ 68
                                      DEEPRobotics

When the velocity command input source of elevation map is joystick, it is called assist
mode, and the elevation map module will process the axis command issued by the
joystick according to the collision detection situation, so as to realize the obstacle
avoidance in the process of manual remote control.
When the velocity command input source of the elevation map is navigation module, it
is called the navigation mode, and the elevation map module will process the velocity
command issued by the navigation module to realize the obstacle avoidance in the
navigation process.

1.5.1.1 Send Command to Switch Velocity Input Source

When using the collision detection function of the elevation map, the control mode

should be switched to the non-manual mode first (refer to 1.2.4), and then the expected

velocity input source can be set by sending the following UDP command to the

perception host 192.168.1.105:43899:

             Command                 Code                       Value         Type
Switching velocity input source  0x3101EE03  1= joystick2= navigation module    0

[Note] Switching between manual and non-manual modes does not reset the elevation map's
velocity input source when it occurs.
[Note] If the joystick app version is lower than v2.3.1, the joystick will automatically reset
the elevation map's velocity input source to joystick when the control mode is switched back
to manual mode from navigation mode or assist mode on the joystick.

1.5.1.2 Receive Messages of Current Velocity Input Source

The port 43899 of perception host will feed back the current velocity input source

1.5.2 Elevation Map Mode

In the process of using the elevation map function, users need to set the correct
elevation map mode for the elevation map according to the actual environment:
1. Before climbing stairs, to ensure that the footstep planning function works properly,

     you need to select the correct elevation map mode according to the type of stairs;
2. In assist mode or navigation mode, to make the elevation map collision detection

     function work properly, you need to select the correct elevation map mode
     according to the environment.
There are four types of elevation map modes: Solid Ground Mode, Grid Ground Mode,
Stair Without Risers Mode and Multi-Frame Mode.

1.5.2.1 Command to Switch to Solid Ground Mode
The solid ground mode is suitable for scenarios where the robot's landing plane is
solid, such as a normal solid concrete flat floor or concrete stairs.

Users can switch to solid ground mode by sending the following UDP message to the
perception host:

The grid ground mode is suitable for scenarios where the robot's landing plane is a

2.4.4 Elevation Map Mode

In the process of using the elevation map function, users need to set the correct
elevation map mode for the elevation map according to the actual environment:
1. Before climbing stairs, in order to ensure that the footstep planning function works

     properly, you need to select the correct elevation map mode according to the type
     of stairs;
2. In assist mode or navigation mode, in order to make the elevation map collision
     detection function work properly, you need to select the correct elevation map
     mode according to the environment.
There are four types of elevation map modes: Solid Ground Mode, Grid Ground Mode,
Stair Without Risers Mode and Multi-Frame Mode.

                                         48/ 68
                                                                        DEEPRobotics

2.4.4.1 Switch to Solid Ground/Grid Ground/Stair Without Risers Mode
The solid ground mode is suitable for scenarios where the robot's landing plane is
solid, such as a normal solid concrete flat floor or concrete stairs.

The grid ground mode is suitable for scenarios where the robot's landing plane is a
grid-like pattern with gaps in between, such as an industrial platform or staircase made
of steel grating panels.

The stair without risers mode is a special condition of solid ground, which refers to a
staircase where the robot places its feet on a solid surface without risers.

2.4.4.2 Switch to Multi-Frame Mode

The muti-frame mode is suitable for scenarios including multiple types of ground

surfaces. For example, if the robot moves from solid ground to grid ground, or from grid
ground to solid ground, it should be marked as composite ground. The obstacle

avoidance function based on the local elevation map is not supported on composite

                                    50/ 68
                       DEEPRobotics

ground, and only composite ground stair gait and 45° stair gait are applicable on

composite ground.
 [Note] Multi-frame mode (including related gaits) is only supported by vmap (1.5.3) and
 needs to be used with jy_exe (1.10.28), launcher (0.0.5), fast-lio (1.0.3), and jycog-system
 (0.5.5).
The steps to switch to the multi-frame mode are as follows (the example code can be

found in Appendix C):

1. Before switching to the multi-frame mode, you need to keep the robot standing still

until it successfully switches to the multi-frame mode.

2. Send the following UDP message to 192.168.1.105:60000 to start the LiDAR-Inertial

Odometry:

the above message:

0xBAA0001              0=Succeed-1=Failed                  0

If it fails, it is necessary to exit from multi-frame mode (refer to 2.4.4.3) before

attempting to start the LiDAR-Inertial Odometry again.

3. After you have successfully start the LiDAR-Inertial Odometry, you can publish

message to the topic /height_map_mode to switch to multi-frame mode:

     Topic Name                   Description            Message Type
/height_map_mode       Choose elevation map mode         std_msgs/Int32

         Multi-Frame Mode                                        20

4. After receiving the message to switch to multi-frame mode, the elevation map

mode after the LiDAR-Inertial Odometry is switched on. Developers can subscribe to
